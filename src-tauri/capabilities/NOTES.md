# How `default.json` was derived — read before changing it

This file did not exist before this pass (`find src-tauri -name capabilities`
returned nothing). Its absence meant a real `tauri dev`/`tauri build` run's
actual permission boundary was undefined — see PHASE-CONTINUITY.md's
standing "ENVIRONMENT-UNVERIFIED" note on this exact point.

## What was actually checked (source, not guesswork)

```
grep -rn "from \"@tauri-apps" src/
```
returned exactly two imports, both from the **core** package, no plugins:
- `@tauri-apps/api/core` → `invoke(...)` — used in `App.tsx` and
  `voice/providers/ElevenLabsTTSProvider.ts` to call this app's own
  `#[tauri::command]`s (`request_action`, `save_provider_key`,
  `elevenlabs_tts`, `add_memory`, `start_remote_control`, etc. — the full
  list in `main.rs`'s `generate_handler![]`).
- `@tauri-apps/api/event` → `listen(...)` — used exactly once, in
  `App.tsx`, for the `"remote-command"` event emitted by
  `src-tauri/src/remote.rs`.

`grep -rn "@tauri-apps/plugin\|tauri-plugin-" src-tauri/Cargo.toml
package.json src/` returned **nothing** — this app uses zero Tauri
plugins (no fs/shell/dialog/notification/clipboard-manager/http plugin).
Every other "external" capability (SQLite, the OS keychain, outbound
HTTP to Anthropic/ElevenLabs/DuckDuckGo, the LAN remote-control TCP
listener) is a plain Rust crate called directly from a `#[tauri::command]`
— none of that goes through Tauri's plugin/permission layer at all, so
none of it needs a capability entry here.

That is the entire permission surface this app's frontend exercises:
invoking its own registered commands, and listening for one event.
`core:default` is Tauri v2's standard bundle for exactly that (app
lifecycle + invoking app-defined commands + event listen/emit) — it is
what `tauri init` scaffolds by default, not a broadened grant added to
make something work.

## What could NOT be verified in this sandbox

- **No `cargo`/Tauri CLI is available here** (unchanged since Phase 1 —
  see every prior session's notes). `tauri dev`/`tauri build` are what
  actually resolve `"core:default"` against the exact `tauri`/`tauri-build`
  crate versions Cargo pins (`"2"`, unpinned patch version) and validate
  this JSON against the real schema. This file is source-reviewed against
  the public Tauri v2 capabilities spec, not build-verified.
- **The `main` window label is assumed, not confirmed.** `tauri.conf.json`'s
  `app.windows[0]` has no explicit `"label"` field; Tauri v2 defaults an
  unlabeled window to `"main"` per its documented schema, but this has not
  been confirmed against a real build's resolved config in this
  environment. If a real `tauri dev` run shows a different effective
  label, update `"windows"` here to match — a capability file that
  targets the wrong window label silently grants nothing.
- **`../gen/schemas/desktop-schema.json` is generated by the Tauri CLI on
  first build**, not something present in this checkout. The `$schema`
  line is inert until that happens (IDE/editor validation only — it does
  not affect runtime enforcement), so its absence pre-build is expected,
  not a bug.

## If a future change needs a new capability

Do not guess a permission identifier. Add the plugin/API, then either run
`tauri dev` once, or check the exact crate/plugin version resolved by
`cargo`/`npm` against Tauri v2's own permission reference for that
package — the naming (`<plugin>:<permission>`) is version-specific enough
that copying an identifier from memory or from an unrelated project's
capabilities file is exactly the "don't guess" case this note exists to
prevent.
